## 0. 一句话定调

> **"数据闭环"不是一条直线管道,是两个相互咬合的飞轮 —— 用户飞轮(business flywheel,业务侧)驱动续费,模型飞轮(model flywheel,技术侧)驱动 AI(Artificial Intelligence,人工智能)越用越懂。咬合点不是技术架构,是 ISOEF(Insight-Strategy-Operation-Evaluation-Feedback,洞察-策略-执行-评价-反馈,五环模型)流程纪律。**

## 第一部分 · 数据闭环的 6 层架构

### 1.1 整体视图

```
┌─────────────────────────────────────────────────────────┐
│ 层 1 · 数据接入层(Multi-Source Ingestion,多源采集)      │
│   企微 AI 对话日志 / 小程序行为事件 / 设备 API 接入        │
│   / 体检报告 OCR(光学字符识别) / 月经日记 / 症状日记      │
│   / 基因数据(华大合作) / 家庭账户关联                     │
├─────────────────────────────────────────────────────────┤
│ 层 2 · 统一健康主权档案(Unified Health Sovereignty)      │
│   一个 user_id 串起 10+ 数据源 · 时序统一 · 跨源去重       │
│   合规层(个保法 / 健康数据敏感分级 / 用户授权流)         │
│   ★ 核心数据资产,5 年时序 = 不可复制护城河                │
├─────────────────────────────────────────────────────────┤
│ 层 3 · AI 解读引擎(L2-L5 价值阶梯)                       │
│   个人 baseline(基线)学习 / 模式识别 / 个性化预测         │
│   RAG(Retrieval-Augmented Generation,检索增强生成)知识库 │
│   :围绝经医学 + 长寿医学 + 中医辨证                       │
├─────────────────────────────────────────────────────────┤
│ 层 4 · 行动输出层(L3 建议 + L6 干预)                     │
│   每日声音简报(早 7:30) / 企微 AI 第一句话(基于上下文)  │
│   / 协议生成 / 真人医师 1on1 转诊 / 同行人小群匹配         │
├─────────────────────────────────────────────────────────┤
│ 层 5 · 反馈收集层(Feedback,最容易被忽视的一环)          │
│   用户是否打开 / 是否照做 / 显式反馈(👍/👎/转发)         │
│   / 状态变化(下一晚睡眠如何)/ 周复盘主观感受              │
├─────────────────────────────────────────────────────────┤
│ 层 6 · Golden Set(评价基准库)+ 模型迭代                  │
│   优秀案例正样本 / 失败案例负样本                          │
│   LLM-as-Judge(用更强 LLM 当裁判)+ Prompt 工程迭代 + 微调 │
└─────────────────────────────────────────────────────────┘
```

### 1.2 每一层的"输入 → 处理 → 输出"

**层 1 · 数据接入层**

| 数据源 | 数据类型 | 频率 | 接入方式 | 优先级 |
|---|---|---|---|---|
| 企微 AI 对话 | 文本日志(用户主诉 / 倾诉 / 提问)| 实时 | 自建 Runtime(运行时)统一记录 | P0 |
| 小程序行为 | 事件总线(打卡 / 点击 / 停留 / 完成) | 实时 | 埋点 + 统一事件流 | P0 |
| Apple Health | 步数 / 睡眠 / HRV(心率变异性) / VO₂max(最大摄氧量) | 每日同步 | 官方 API(应用程序接口) | P0 |
| 华为运动健康 | 同上,中国本土用户主力 | 每日同步 | 华为开放平台 API | P0 |
| 月经记录 | 周期 / 经量 / 症状 | 每日用户主动录入 | 小程序内嵌表单 | P0 |
| 症状日记 | 潮热次数 / 情绪 / 心情 | 每日用户主动录入 | 小程序内嵌 + 企微对话识别 | P0 |
| 体检报告 | PDF / 图片 | 用户上传时 | OCR + LLM(大语言模型)结构化解析 | P1(Phase 1 注入) |
| 设备数据(Oura / Whoop / Garmin) | 戒指 / 手环 / 跑表数据 | 每日同步 | 各家官方 API | P1 |
| 基因数据 | 基因型 + 风险评分 | 一次性 | 华大基因合作回传 | P2 |
| 上游检测(金域 / 瑞慈) | ApoB(载脂蛋白 B) / Lp(a)(脂蛋白 a) / HOMA-IR(胰岛素抵抗指数) / hs-CRP(超敏 C 反应蛋白) | 每 6 个月 | 战略合作 API + 数据回传协议 | P2 |
| 家庭账户 | 父母 / 配偶 / 子女健康数据 | 各自频率 | 多账户绑定 + 隐私分级 | P2 |

**层 2 · 统一健康主权档案**

核心数据模型:
```
user
├── identity(身份)
│   ├── user_id(全局唯一)
│   ├── 生命阶段(围绝经前期 / 活跃期 / 过渡期 / 绝经后)
│   ├── 穿越天数(从产品注册日 / 自定义起点)
│   └── 家庭账户关系(本人 / 父亲 / 母亲 / 配偶 / 子女)
├── data_sources(数据源清单)
│   └── [接入状态 + 最近同步时间 + 数据完整度]
├── timeline(时序记录)
│   ├── biometric(生理数据,Apple Health 等)
│   ├── lab(检测数据,金域 / 瑞慈 / 体检中心)
│   ├── diary(主观日记,月经 / 症状 / 心情)
│   ├── ai_interaction(与 AI 的所有交互)
│   └── intervention(干预与执行,协议 / 推荐 / 完成情况)
├── derived(衍生指标 · AI 计算输出)
│   ├── biological_age(生物年龄)
│   ├── perimenopause_phase(围绝经阶段判定)
│   ├── trigger_patterns(触发模式 · 如"加班 3 天后 HRV 跌 5")
│   └── risk_signals(风险信号 · L5 预测层)
└── consent(用户授权)
    ├── 数据使用范围
    ├── 第三方共享授权
    └── 家庭数据互访授权
```

合规要求(中国 + 跨境兼容):
- 《个人信息保护法》(2021)健康信息敏感分级
- 《数据安全法》(2021)数据出境合规
- HIPAA(Health Insurance Portability and Accountability Act,美国健康保险流通与责任法案)等价框架(为未来海外华人 + 国际用户准备)

**层 3 · AI 解读引擎**

技术栈分层:
| 层 | 用途 | 推荐选型 |
|---|---|---|
| 通用大模型 | 一般对话、共情、知识问答 | 豆包(主) + DeepSeek(副) + 国际版 Claude / GPT(海外用户备份) |
| 个性化模型 | 学习单个用户的 baseline(基线)和 reflex(独特反应) | 每用户独立 embedding(嵌入向量)+ 长期记忆库 |
| 预测模型 | L5 层 · 预测疾病 / 状态变化 | 基于历史时序的小模型(LSTM / Transformer 变种) |
| RAG 知识库 | 围绝经 + 长寿 + 中医辨证 | 自建向量数据库 + 医学 IP 合伙人审定 |

**层 4 · 行动输出层**

输出类型:
- **声音简报**(早 7:30,3-5 分钟)= 关系货币 + 认知货币 + 安全感货币 三合一
- **企微 AI 主动消息**(早间问候 / 计划跟踪 / 周报推送)= 进步货币
- **协议生成**(基于个人数据的 14 天 / 30 天 / 90 天行动计划)= 成就货币
- **真人医师 1on1 转诊**(Phase 1.5 后)= 安全感货币 + 身份认同
- **同行人小群匹配**(同年龄 ±3 + 同状态)= 关系货币 + 身份归属

**层 5 · 反馈收集层(最关键)**

3 种数据源:
| 数据源 | 信号类型 | 回流作用 |
|---|---|---|
| 用户行为数据 | 点击 / 停留 / 跳出 / 转化 | 修正个性化模型 → 调整下一轮 Insight 假设 |
| 用户显式反馈 | 打分 / 评论 / 举报 / 客诉 / 续费 | 识别 Agent 失败模式 → 进 Golden Set 负样本库 |
| Agent 自身日志 | 调用链 / 错误 / 低置信度输出 | 识别 Prompt / Tool 设计问题 → 触发 Operation 迭代 |

**层 6 · Golden Set 与模型迭代**

构建 SOP:
1. 从真实业务场景抽取 50-200 个有代表性输入样本
2. 由"领域专家"(中国版 Mary Claire Haver 玛丽·克莱尔·海弗 / 内部医学顾问 / 资深 PM)给出"理想输出"或"评分维度 + 评分标准"
3. 评分维度:相关性 / 准确性 / 完整性 / 安全性 / 风格一致性 / 围绝经语境适配,各维度 1-5 分
4. Golden Set 必须有版本号、必须 review、必须随业务演进持续更新

LLM-as-Judge 关键约束:
- 评判 LLM 必须比被评判 LLM 更强(用 Claude Sonnet 评 DeepSeek;用 Claude Opus 评 Claude Sonnet)
- LLM-as-Judge 输出本身要定期用人工抽样校准(AI 评 AI 不是免检)
- 成本敏感:Judge 调用本身有成本,要做采样而非全量评判

## 第二部分 · 双飞轮咬合的真正机制

### 2.1 用户飞轮(业务侧)

```
AI 服务用户(声音简报 / 企微对话 / 协议执行)
        ↓
用户产生新行为(打开 / 跟做 / 反馈 / 续费)
        ↓
行为数据沉淀到层 1-2
        ↓
习惯养成模型升级(发现这个用户独特的"触发模式")
        ↓
个性化更精准(下次 AI 说的话更"懂她")
        ↓
用户价值提升(她感觉"被持续管理 + 被记得")
        ↓
更多用户来(NPS 拉动 + 家庭账户拉新)+ 更高续费(L0→L1→L2→L3)
        ↓
回到顶部,飞轮加速
```

**核心信号:用户密度**(同一用户的交互频次 × 数据完整度)

### 2.2 模型飞轮(技术侧)

```
Agent 处理任务(回答用户 / 生成简报 / 给协议)
        ↓
产生交互日志(每一次输入 + 输出 + 置信度)
        ↓
失败 / 低置信度 case 进 Golden Set 候选池
        ↓
评价系统识别系统性问题(这类问题集中失败 / 那类用户群体偏弱)
        ↓
触发 Prompt / Tool / 微调迭代
        ↓
Agent 能力升级 → 处理更复杂任务
        ↓
回到顶部,模型飞轮加速
```

**核心信号:Case 多样性**(遇到的边界 case 越多 + 沉淀越完整,模型飞轮转得越快)

### 2.3 两个飞轮的咬合点 = 公司自建 AI Runtime

```
              用户飞轮(业务北极星)
                     ▲
                     │
                     │  ┌── 个性化更精准
                     │  │
              ┌──────┴──┴──────┐
              │  统一 Runtime  │  ← 飞轮咬合点
              │  + 数据沉淀    │
              └──────┬──┬──────┘
                     │  │
                     │  └── 模型能力升级
                     │
                     ▼
              模型飞轮(技术北极星)
```

**关键判断**:咬合点不是数据中台,是**强制所有 AI 调用走同一通道 + 全量日志沉淀 + Golden Set 持续运营**。任何一个团队成员/部门/PA(流程智能体)单独调用外部 LLM API(应用程序接口),咬合点就开个口子,飞轮就漏气。

## 第三部分 · Day 0 必须做的最小可行底座(MVP)

来源:AI 原生方法论 4.3 节"飞轮启动期的最小可行底座"。

| # | 底座 | 是什么 | 为什么 Day 0 必做 |
|---|---|---|---|
| 1 | **统一 Runtime + 调用日志** | 公司所有 AI 调用走同一通道,日志全量入库 | 不走统一通道 = 飞轮没有起点,数据散在豆包 / DeepSeek / Claude API 各自后台,**永远无法整合** |
| 2 | **用户行为事件总线** | 把企微 / 小程序 / 设备数据 与 Agent 调用日志关联,形成 "Agent → 行为 → 业务结果" 因果链 | 没有这个 = 无法判断"AI 这次说话之后用户行为变了没有",**反馈环不通** |
| 3 | **Golden Set 起步库** | 每个 PA(流程智能体)100-200 条标注样本起步,持续更新 | 没有 Golden Set = 任何 Prompt 变更都是赌博,**无法判断"改了之后是变好还是变差"** |

**这三件东西建好,飞轮就能启动。其余基础设施可以边跑边补。**

## 第四部分 · 三大执行死穴(绝大多数团队栽在这里)

### 4.1 死穴一 · E(评价)环节没有 Owner

> ISOEF 五环里 E(评价)最容易死。它跨职能、出力不出彩——做 Golden Set 的人不光要懂业务还要懂 AI,但绩效又不直接体现为业务结果。

**悦龄的应对**:
- 每个 PA(失眠 / 体重 / 情绪 / 家庭压力)配一个"评价负责人"
- 向 PA 业务负责人 + Builder 负责人 **双线汇报**
- 这个角色应该是 **P0 级别配置**,不是"找个 PM 兼任"
- KPI 包括:Golden Set 大小 / 新增节奏 / 失败 case 转化率 / Prompt 迭代触发次数

### 4.2 死穴二 · F(反馈)节奏没有强制

> 做完一个 Agent 上线后,所有人都想转到下一个新项目,没人愿意回来看上一个。

**悦龄的应对**:
- "Agent 项目"改名为 "Agent 产品" — 产品有版本、有 roadmap(路线图)、有持续 owner
- 每周一固定生成"异常 case 报告",PM + 算法 review
- 每月触发一次 Insight 回顾(奖励类型分布是否变化?是否有新的奖励类型出现?)
- 迭代级别明确:微调 Prompt(每周)/ 调整 Tool(每月)/ 重做 Strategy(每季度)

### 4.3 死穴三 · 数据回流不自动化,靠人工"看一下"

**推荐架构:**

```
用户行为日志 → 自动入数仓
       ↓
Agent 日志 → 自动打标签(场景 / 意图 / 置信度)
       ↓
每周一自动生成"异常 case 报告"
       ↓
异常 case 自动进 Golden Set 候选池
       ↓
PM / 领域专家(医学 IP 合伙人 / 内部顾问)Review
       ↓
入 Golden Set
       ↓
触发下一轮 Prompt / Tool / 微调
```

**判断悦龄 Feedback 成熟度,只问 3 个问题:**
- 上次根据线上反馈触发迭代是什么时候?(超过 30 天 = Feedback 不通)
- 用户的负面反馈,有没有自动进入下一轮 Golden Set?(没有 = 反馈没有沉淀)
- Agent 的失败 case,有没有反向驱动 Insight 重做?(没有 = 不是真闭环)

## 第六部分 · 美国三家的失败警示

| 公司 | 失败时刻 | 教训 |
|---|---|---|
| **Function** | 2025 年 11 月才推出 MI Lab(Medical Intelligence Lab,医学智能实验室)——AI 起步晚 3 年 | "检测先行 + AI 后置" = 前 3 年只是 D2C(Direct-to-Consumer,直接面向消费者)检测公司,数据飞轮起步太晚,Reddit(美国社区论坛)早期会员批评"clinician report essentially ChatGPT"(临床医师报告本质上是 ChatGPT 水平) |
| **Whoop** | 13 年只做手腕带数据,2025 年才加血液检测 | 跨源整合直到 2025 年才开始(Advanced Labs 血液检测整合)→ 错过早期"多源数据飞轮"窗口 |
| **Oura** | 早期所有数据归类于"睡眠" | 后期推女性健康时,模型架构需要 retraining(重训练),成本高 |

**我们 Day 0 就避开这些坑的方式:**
- **AI 先行**(不要 Function 弯路)— AI 与数据飞轮从注册第 1 个用户就开始
- **Day 0 就做 device-agnostic**(设备无关)多源接入(不要 Whoop 弯路)— Apple Health + 华为 + 主观日记三源齐发
- **数据模型一开始就预留性别 / 生命阶段维度**(不要 Oura 弯路)— 即使 MVP 只服务女性,数据架构支持后续男性灯塔合并

## 第十部分 · 给悦龄团队的"3 个生死问题"

让任何技术/产品方案过审前,先回答这 3 个问题。如果有一个答不上,方案就不要上线:

| # | 问题 | 致命点 |
|---|---|---|
| 1 | **这次改动产生的数据,有没有自动进入统一 Runtime + 行为事件总线?** | 答否 = 飞轮漏气,贡献为 0 |
| 2 | **这个 Agent 失败时,失败 case 会不会自动进 Golden Set 候选池?** | 答否 = 没有反馈环,模型不会变好 |
| 3 | **Prompt 改了之后,有 Golden Set 跑评测吗?能用数字说"变好"还是"变差"吗?** | 答否 = 改 Prompt 就是赌博,迟早翻车 |
